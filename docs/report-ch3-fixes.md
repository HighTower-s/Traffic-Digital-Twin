```json
"zones": { "in": {...}, "out": {...} }     ← ของจริง
"zones": [ {...}, {...} ]                  ← ส่งแบบนี้ backend ตอบ HTTP 400
```

## 2. §3.3.1 — ย่อหน้านิยามทิศทาง 🔴 ผิดที่สุดในบท

ย่อหน้าที่ขึ้นต้น *"จากมุมกล้องดังกล่าว ผู้จัดทำกำหนดนิยามทิศทางไว้ว่า..."*
จบที่ *"...จนถึงการสร้างยานพาหนะในแบบจำลองสามมิติ"*

**ผิดเพราะ** ระบบแยก 2 แนวคิดออกจากกันแล้ว

| | `expectedDirection` | `direction` |
|---|---|---|
| ค่า | `toward` / `away` | `in` / `out` |
| มาจาก | ทิศที่รถเคลื่อนที่ในภาพ | **ชื่อโซน** (`ai-worker/src/emitter.py:50`) |
| ใช้ทำอะไร | ปฏิเสธรถที่วิ่งสวนทาง (§3.5.3) | ส่งออกให้ Unity |

ของจริงใน `configs/event-2.yaml` คือ `name: in` คู่กับ `expectedDirection: away`
ซึ่งย่อหน้าปัจจุบันบอกว่าเป็นไปไม่ได้ และประโยค *"ถูกใช้ตลอดทั้งระบบ...จนถึงการสร้าง
ยานพาหนะในแบบจำลองสามมิติ"* ผิดชัดที่สุด เพราะ Unity ไม่เคยได้รับ `toward`/`away` เลย

```latex
จากมุมกล้องดังกล่าว ผู้จัดทำกำหนดนิยามการเคลื่อนที่ในภาพไว้ว่า ยานพาหนะที่เคลื่อนที่
เข้าหากล้องจะปรากฏเป็นการเลื่อนลงด้านล่างของภาพ กำหนดให้เป็นค่า \texttt{toward}
ส่วนยานพาหนะที่เคลื่อนที่ออกจากกล้องจะปรากฏเป็นการเลื่อนขึ้นด้านบนของภาพ กำหนดให้เป็นค่า
\texttt{away} นิยามนี้เป็นเรื่องของเรขาคณิตในภาพล้วน ๆ และถูกใช้ในการตรวจทิศทาง
การข้ามเส้นตามหัวข้อที่ \ref{subsec:direction-check} เพื่อปฏิเสธยานพาหนะที่เคลื่อนที่
สวนทางกับที่โซนนั้นรับผิดชอบ

ส่วนทิศทางที่ระบบส่งออกไปยังโมดูลปลายทาง คือค่า \texttt{in} หรือ \texttt{out} นั้น
กำหนดจากชื่อของโซนโดยตรง ไม่ได้คำนวณจากทิศการเคลื่อนที่ในภาพ ผู้จัดทำแยกสองสิ่งนี้
ออกจากกันเนื่องจากความสัมพันธ์ระหว่างฝั่งถนนกับทิศการเคลื่อนที่ในภาพขึ้นอยู่กับว่ากล้องถูก
ติดตั้งหันไปทางใด การผูกค่าทั้งสองเข้าด้วยกันจึงทำให้ต้องแก้โปรแกรมทุกครั้งที่เปลี่ยนมุมกล้อง
ผลของการแยกคือโซนหนึ่งสามารถมีชื่อเป็น \texttt{in} ขณะที่ยานพาหนะในโซนนั้นเคลื่อนที่
ออกจากกล้อง (\texttt{away}) ได้ ซึ่งเป็นกรณีที่เกิดขึ้นจริงกับชุดข้อมูลที่ใช้ทดสอบ

ข้อจำกัดนี้ถูกพบระหว่างการพัฒนา เมื่อผู้จัดทำกำหนดโซนใหม่ให้ตรงกับฝั่งถนนที่ต้องการรายงาน
ระบบรุ่นก่อนหน้าซึ่งกำหนดให้ \texttt{toward} มีค่าเท่ากับ \texttt{in} เสมอ ได้ปฏิเสธ
ยานพาหนะด้วยเหตุผลว่าเคลื่อนที่สวนทางถึง 105 รายการ คิดเป็นความผิดพลาดของการนับ
ประมาณร้อยละ 98 การแก้ไขให้ทิศทางที่ส่งออกอ้างอิงจากชื่อโซนทำให้ปัญหานี้หมดไป
```

> ย่อหน้าที่ 3 ใส่หรือไม่ใส่ก็ได้ แต่เป็นหลักฐานเชิงประจักษ์ที่ตอบกรรมการได้ดี

## 3. §3.3.2 — ย่อหน้าจำนวนโซน 🟠

ย่อหน้าที่เขียนว่า *"ผู้จัดทำกำหนดโซนตรวจวัดไว้**หนึ่งโซน** คือโซนทิศทางเข้า เนื่องจาก
ช่องจราจรฝั่งตรงข้ามอยู่ไกลจากกล้องและถูกบดบังมากเกินกว่าจะตรวจนับได้อย่างน่าเชื่อถือ"*

**ขัดกับรูปที่ 3.4 ในหน้าเดียวกัน** ซึ่งแสดง 2 โซน (ฟ้า + เหลือง) และขัดกับระบบจริงที่ตัดสินแยกรายโซน

```latex
ในการตั้งค่าที่ใช้ทดสอบ ผู้จัดทำกำหนดโซนตรวจวัดไว้สองโซน ครอบคลุมช่องจราจรทั้งสองฝั่ง
ของถนน โดยโซนหนึ่งรับผิดชอบทิศทางเข้าและอีกโซนหนึ่งรับผิดชอบทิศทางออก เหตุผลที่ต้อง
แยกสองโซนคือถนนทั้งสองฝั่งไม่ได้ติดขัดพร้อมกัน จากข้อมูลที่วัดได้จริง ครึ่งหนึ่งของหน้าต่างเวลา
ทั้งหมดมีสถานะของสองฝั่งแตกต่างกัน การรายงานค่าเดียวสำหรับทั้งภาพจึงกลบข้อมูลที่สำคัญไป
ระบบจึงรายงานสถานะแยกรายโซนควบคู่ไปกับค่ารวม โซนนับ เส้นนับ และโซนวัดความหนาแน่น
ที่วาดทับบนเฟรมจริง แสดงในรูปที่ \ref{fig:zones}
```


### ย่อหน้าที่มาของเกณฑ์ (ใส่เพิ่มได้)

```latex
ค่า $O \geq 4.0$ ถูกกำหนดจากจุดที่อัตราการไหลลดลงอย่างฉับพลันในข้อมูลที่วัดได้จริง
กล่าวคือ ที่ความหนาแน่น 3.77 คันต่อเฟรม อัตราการไหลมีค่า 12 คันต่อนาที แต่เมื่อความหนาแน่น
เพิ่มเป็น 4.19 คันต่อเฟรม อัตราการไหลลดลงเหลือ 3 คันต่อนาที ซึ่งสอดคล้องกับแนวคิด

การจราจรติดขัดที่สังเกตได้จริง ซึ่งมักเป็นการเคลื่อนตัวคืบหน้าทีละเล็กน้อยมากกว่าการหยุดนิ่ง
สนิทตลอดทั้งหน้าต่าง ค่า $7.5$ หมายถึงยอมให้มีรถยนต์ผ่านเส้นนับได้ไม่เกิน 2 คันต่อหน้าต่าง

เกณฑ์ใหม่ ซึ่งสอดคล้องกับลักษณะการจราจรที่ปรากฏมากกว่า
```
